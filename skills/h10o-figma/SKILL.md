# Figma の画面をサイト全体に揃えて実装する

色、余白、部品、表記をサイト全体で1つに揃える。デザインファイルに無いことは推測で埋めない。このスキルが決めている判断は、依頼文が逆のことを言っていても従う。戻せと明示されたときだけ戻す。

## 手順

部品は1つずつ、次の順で進める。順を飛ばさない。

1. 依頼を自分の言葉で言い直して返す。範囲、やらないこと、成果物の形を短く書く。揃ってからファイルを変える。
2. 渡された URL のノードを読む（「読み方」）。読めたかと、どの手段で読んだかを報告する。
3. プランを返す。全ページ共通の UI と下層ページ共通の枠の置き場所を先に決める。今ある部品、レイアウト、トークンを見て、合うものは再利用するか足して使い、無いものだけ新しく作る。共有の部品や、すでにある下層ページを、デザインに合わせるために一から作り直さない。
4. 実装する。頼んだ箇所だけ変える。ほかの UI や、直前に決めた寸法をついでに変えない。
5. 実装した画面をデザインの画像と見比べて直す（「見比べる」）。
6. テストと CI を通してコミットする。同じ話題の変更は今あるブランチと PR に載せる。

ページ全体のノードを渡されたときは、一度に全部を実装しない。セクションなどの単位に分け、単位ごとにこの順を回してから次へ進む。一度に全部作ると精度が下がる。

人が画面を見るまでマージしない。CI が緑でもマージしない。マージするかは依頼者が決め、エージェントはマージしない。

スタイルを当てないと依頼されたときは、データと構造だけの部品で止めてよい。スタイルまで求められた依頼を、構造だけで完了にしない。

見本ページは普通の案件では作らない。求められたときだけ出す。

## 読み方

渡された URL のノードを、どの部品を見るかの正本にする。キャンバスで選択中のノードは正本にしない。部品ごとに、コンポーネントかコンポーネントセットのノードを1つ受け取る。

値はマスターから取り、インスタンスで上書きされた値は使わない。実例は、インスタンスの 56px ではなくマスターの 64px に合わせたことである。

読めなかったら推測で実装しない。

ファイルから書き出せない素材は自分で作らず、依頼者に頼む。

## デザインに無いこと

依頼文に狭い画面、多いデータ、折り返し、ホバーと書いてあれば、デザインファイルに無くても設計に含める。

件数の違いや 0 件のように、依頼文にもデザインにも無いデータの状態は、未確定として残してデザイン担当に確認する。このスキルが決めている見た目までは未確定に戻さない。

振る舞いがファイルで決まっていないときは、依頼で渡された実在のサイトを参考にしてよい。借りるのは振る舞いだけで、見た目はデザインファイルに従う。

同じデータの表記が1画面だけ違うときは、デザインファイルを直さず、実装でサイト全体の形に揃える。投稿日の実例は `YYYY.MM.DD`（例 `2024.04.24`）である。本文中の日付（令和の表記や「12月1日（月）」など）は投稿日ではないので、この形にしない。

デザインファイルのホバーは、そのまま採るとは限らない。採ったもの、採らなかったもの、却下した案はコミットに残す。依頼者が戻すと言ったら戻す。

## 見比べる

デザインの画像がある画面は、実装した画面をその画像と見比べてから先へ進む。画像が無い画面（管理画面など）は、動いているページを人が見られる状態にして見せ、無い画像を待って止めない。ページを出せないときは、出せない原因を直す。見比べは、人が目で見ることと、貼られた画面への指摘で行う。差分画像は要らない。

狭い画面ととても広い画面の両方を見る。実例の幅は 390、1000、1440、1920 である。ページ全体を2倍で書き出して見比べない。

完了条件は、画像がある画面では見比べたこと、そしてテストと CI の通過である。スクリーンショットの有無だけを完了条件にしない。

## 色

色は2層にする。プリミティブは生の色値を置く層、セマンティックはデザインファイルのセマンティック名を使う層である。セマンティックは必ずプリミティブを参照し、直値を残さない。部品はセマンティックだけを使う。すでにセマンティックとして使える色を、もう1段プリミティブで包まない。

名前は1つにする。同じ色の別名や、層を示す接頭辞を残さない。新しい名前は、今ある名前と意味がぶつからないか確かめてから決める。濃さの系列がある色は、その系列の中の名前にする。ホバー用の色もセマンティックトークンにする。

デザインファイルで変数になっていない色は、使う場所の名前で専用トークンにし、プリミティブを参照する。フッターのグラデーションをその場所の名前にしたのが実例である。

色の正本は1つのファイルに置く。共有する色は正本から生成し、二箇所に手で書かない。生成結果は変数参照を残し、実値をベタ書きしない。

段階色は 100 から 900 まで（必要なら 50 も）、プリミティブに直値で置く。プリミティブをほかの色を混ぜて作らない。混ぜるのは使う側だけである。段階を足したら、既存の値が変わっていないか確かめる。

スタイリングシステムの既定カラーパレットは消して、プロジェクトのトークンだけにする。消したことは検査で固定する。

管理画面だけの意味トークン（状態の色）は、管理画面のスタイルに置き、公開サイトの正本に足さない。プリミティブは共有してよい。状態の色は、意味がひと目で分かる強さを保つ。

## 書体

スタイリングシステムに既定の文字サイズスケールがあれば、そこにあるサイズはその名前を使い、無いサイズだけトークンを足す。独自のスケールを作らない。

文字サイズを指定しても、本文の行間を潰さない。和文本文の実例は行間 1.8、字間 0.04em である。

画面幅で文字サイズを変えるのは、大きい欧文の見出しだけである。その見出しはマスターのサイズに合わせ、狭い画面で調整する。

フォントの指定は部品ごとに書かず、ベースに置く。説明の文に飾りの書体や英字ラベルを足さない。書体の読み込み方は案件ごとに選び、方法を固定しない。

## 余白とサイズ

スケールやトークンに名前がある寸法を、その場だけの px で書かない。名前の無い数値を、見た目が同じ別の値へ直すかは自分で決めない。

間隔と幅はスタイリングシステムの標準スケールを使う。独自の余白トークンは、ページの左右余白のようにページ間で共通の式だけにする。

ページ間で共通の縦の余白はレイアウト部品が持ち、ページ側では指定しない。狭い画面では広い画面の半分にする（実例 80px → 40px）。

左右の余白は幅の帯で分ける。中間の幅では本文が細くならないよう下限を固定値にする。実例は、768px 以上で下限を画面幅の 12.5% から 40px にし、1440px で左右 180px、本文を 1080px で止めたことである。狭い画面で左右の余白が消えているときは、ゼロにせず比率で残す。縦に積み替えたら左右余白を詰める（実例 20px）。

余白は表示した結果を見て1段ずつ詰める。閉じた開閉部品が本文の行間より広く見えるとき、テキストとアイコンの間隔が広いときも、見た目に合わせて詰める。

縦の揃えは箱の中央ではなく字面で合わせる。複数行のときは、アイコンや日付を1行目の中央に置く。形の重心で下に見える印は、文字の横に置くときだけ 1px 上げる。

部品は自分を親の幅いっぱいにしない。基本は中身の幅で、いっぱいにするかは置く側が決める。

写真の枠は、とても広い画面でもデザインの大きさで止める。

## 画面幅

切り替え幅は、フレーム幅ではなく中身が収まるかで決める。約 900px で6項目とロゴが1行に収まるため、より広い区切りを選んだのが実例である。グリッドの列数は画面幅で変える。

狭い画面、大量のページ、長い現在地、長いタイトルでも崩さない。長い現在地は行の中で折り返す。

狭い画面では背景を画面の端まで出してよい。文字の左端はページの余白に揃え、そのために余白を縮めない。

データの表は、狭い画面でカードにせず横にスクロールさせる。

## ホバーと動き

色の変化と開閉の長さはトークン1つで決める。基準は 250ms で、部品ごとに直書きしない。

ホバーは変わったと分かる差にする。部品全体の不透明度を下げない。押せるものにはホバーを付ける。ページ送りとテキストリンクにも色の変化を付ける。

一覧とカードのホバーは、下線ではなく色を変える。日付などのメタ情報も同じ色に変える。本文のテキストリンクは、下線と色の両方を変える。下線はラベルの範囲だけで、アイコンには付けず、二重にしない。ボタンには下線を付けない。ページ内アンカーの下線は、ホバーで色も変える。

開閉部品では、開いた状態とホバーで色を割らない。ホバーの面と押せる範囲は部品全体にする。開くときも閉じるときもなめらかに動かす。

ナビゲーションの現在地とホバーは同じ表現にする。実例は、濃い文字色と中央から伸びる 1px の下線である。

固定ヘッダーの下端は、ヘッダー範囲の外側でフェードさせる（実例 16px）。ヘッダーの範囲では不透明度とぼかしを変えず、裏の画像をロゴ越しに透かさない。

同じ種類のボタンはホバーも揃える。本文に出るファイルのボタンも、対応するボタンに合わせる。

## 部品

同じ UI と同じ処理（投稿日の整形など）は、ページをまたいで1つにまとめる。既存の部品で足りるなら、新しく作らずそれを包む。

CMS が出す本文にも同じ見た目が当たるように設計する。本文リンクの印は呼び出し側で出してもよいが、出し方はサイト全体で1つにする。

置き場所は役割で分ける。見た目だけの部品、コンテンツの種類ごとの部品、CMS に依存する部品を混ぜない。見た目だけの部品が CMS の型やデータを import できないように検査する。

部品名をデータの種類に縛らない。依存しているのがパスだけなら、特定のコンテンツ名を入れない。

見た目のためだけの独自の指定は避ける。同じ指定の列を呼び出し側に毎回書かせず、部品の中に1回だけ書く。variant と呼び出し側の指定は部品の中で合成し、衝突したら呼び出し側が勝つ。合成の処理を別ファイルに出さない。

前後の移動のように対になる操作で片方が無いときは、空欄にせず灰色の押せない見た目で残す。押せない状態と現在地は見た目で示す。

## アイコンと画像

アイコンは管理と使い方を決めてから実装し、1つの部品に集める。ボタンと本文のファイルのボタンで同じマークを使う。向きはデザインファイルと照らし、上下や回転を勝手に変えない。SVG には寸法を与え、箱だけを大きくしない。

ブランドのロゴは、デザインファイルの中の画像ではなく公式の配布素材を元にする。形式は中身を見て選ぶ。ベクターなら SVG にする。中身が画像のままのベクターはベクターとして扱わず、ラスター画像として WebP にする。

画像は使う場所のフォルダに置き、ファイル名は `img-` のあとに役割だけを書く（実例 `assets/images/page/img-hero.webp`）。2倍幅の画像は、同じ名前の末尾に `@2x` を付ける（`img-hero@2x.webp`）。外れたファイルは検査で落とす。

ラスター画像は、写真も透過のある画像も WebP にする。jpg や png の予備は置かない。アイコンとロゴは SVG にする。

ラスター画像は Figma から2倍で書き出し、表示幅と2倍幅の2枚を WebP で作る（60px 表示なら 60px と 120px）。品質は 80 程度にする。`srcset` には幅（`w`）で2枚を並べ、`sizes` は画面に出る幅どおりに書いて2倍にしない。

写真の重ね効果（色の膜やグラデーション）は、写真を素のまま書き出し、実装側で重ねる。CMS から入る写真にも同じ効果が付き、色はトークンで変えられる。実装で再現しにくい複雑な効果だけは、書き出しに含めてよい。

favicon と OGP 画像は環境ごとの条件に合わせる。WebP の規則の外に置き、タッチアイコンは PNG、OGP 画像は JPEG か PNG にする。タッチアイコンは 180px の白背景にする。仮の favicon を残さない。ページが OGP 画像を渡さないときは、サイト共通の画像を出す。

## マークアップ

見出しの階層は見た目と分ける。h1 はそのページの記事タイトルにし、サイト名を h1 にしない。ラベルとして見える見出しは `p` にする。

開閉は `details` と `summary`、モーダルは `dialog` で作る。

ページタイトルの区切りはサイト全体で1つにする。実例は全角の縦棒 `｜` である。

## スタイルの書き方

スタイリングシステムに登録されていない指定は、その検査があるときは落とす。検査から外す独自の名前は、プロジェクトの接頭辞で始める。

組版用のスタイルとぶつかる指定は、組版側に勝つ層へ移す。表のセルの余白や、文字が上に寄る問題はここで直す。

ベーススタイルは部品と同じ書き方に揃える。

## 管理画面

管理画面は、そのシステムの標準 UI に合わせる。独自の見出し、フォント、ページ全体の最大幅を足さない。細かいところは標準の部品で無理なく作れる形にする。

本文の無いデータに、本文用のキャンバスを付けない。機能は見た目の層に書かない。関連する設定は1画面でまとめて見えるようにする。カードの幅は枠ごと揃え、右側だけが空く見え方にしない。公開状態は、まとまりと状態の表示でひと目で分かるようにする。

新しく書く文言は、よく使われる言い方で、今の種類だけに閉じない名前にする。担当者がすでに直した文言は正とし、あとから渡された仕様の表の文言へ戻さない。

## 検査、コメント、コミット

機械で検査できるルールは lint や検査に移し、違反メッセージに理由と直し方を書く。文章と検査を二重に持たない。IDE の警告も、拾えるなら検査に入れる。色の一回きりの値を落とす検査は、サイズとグリッドまでは見ない。名前がある寸法を、別の検査で落とすのはよい。

渡し忘れは隠さない。型があるときは型で落とし、既定値や既定の画像で埋めない。

コメントは、あえてやらなかった理由だけにする。意味は名前で表す。

定数を書き写しただけのテストと、文言や幅を名指しで固定するテストは書かない。

担当者が直接入れたコミットは、戻す指示が無い限り戻さない。

コミットメッセージは日本語で、意図、決めたこと、却下した案が分かるように書く。`intent`、`decision`、`rejected` と書いてよい。

ドキュメントはコードと突き合わせて直し、違う記述と古い記述は削る。

このスキルに書いた判断は、ライブラリの定石で上書きしない。書いていない判断は、公式のベストプラクティスや有名な UI ライブラリ、デザインシステムと照らして決める。聞かれたら変更の目的を説明する。

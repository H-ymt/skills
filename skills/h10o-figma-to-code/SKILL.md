# Figma の画面をサイト全体に揃えて実装する

色、余白、部品、表記をサイト全体で1つに揃える。デザインファイルに無いことは推測で埋めない。狭い画面のフレームが無いときは、推測ではなく [visual.md](references/visual.md) の規則で導く。このスキルが決めている判断は、依頼文が逆のことを言っていても従う。戻せと明示されたときだけ戻す。

## 手順

部品は1つずつ、次の順で進める。順を飛ばさない。

1. 依頼を自分の言葉で言い直して返す。範囲、やらないこと、成果物の形を短く書く。揃ってからファイルを変える。
2. 実装済みのページがあるときは、共有のレイアウト、トークン、同じ種類のページを1つ読む。基本をそこで固定する。基本は、左右の余白、セクションの縦の間隔、書体、共有の部品である。1ページだけの一回きりの寸法は基本にしない。実装済みのページが無いときは、最初のページで基本をレイアウトに置く。ページ側の数値にしない。この固定は依頼ごとに1回である。
3. 渡された URL のノードを読む（「読み方」）。読めたかと、どの手段で読んだかを報告する。ノードから取るのは、画面にあるものと、部品そのものの大きさである。基本に決めた余白や書体を、ノードの測った数で置き換えない。
4. 触る領域の参照だけを読む。プランを返す。全ページ共通の UI と下層ページ共通の枠の置き場所を先に決める。今ある部品、レイアウト、トークンを見て、合うものは再利用するか足して使い、無いものだけ新しく作る。共有の部品や、すでにある下層ページを、デザインに合わせるために一から作り直さない。
5. 実装する。頼んだ箇所だけ変える。ほかの UI や、直前に決めた寸法をついでに変えない。
6. 実装した画面をデザインの画像と見比べて直す（「見比べる」）。
7. テストと CI を通してコミットする。同じ話題の変更は今あるブランチと PR に載せる。

ページ全体のノードを渡されたときは、一度に全部を実装しない。セクションなどの単位に分け、基本の固定のあとは単位ごとに手順 3 から回す。一度に全部作ると精度が下がる。

人が画面を見るまでマージしない。CI が緑でもマージしない。マージするかは依頼者が決め、エージェントはマージしない。

構造だけの部品は、毎回の手順ではない。スタイルを当てないと依頼されたときだけ、データと構造だけの部品で止めてよい。スタイルまで求められた依頼を、構造だけで完了にしない。

見本ページは普通の案件では作らない。求められたときだけ出す。

## 読み方

渡された URL のノードを、どの部品を見るかの正本にする。キャンバスで選択中のノードは正本にしない。部品ごとに、コンポーネントかコンポーネントセットのノードを1つ受け取る。

値はマスターから取り、インスタンスで上書きされた値は使わない。実例は、インスタンスの 56px ではなくマスターの 64px に合わせたことである。

読めなかったら推測で実装しない。

ファイルから書き出せない素材は自分で作らず、依頼者に頼む。

## デザインに無いこと

依頼文に狭い画面、多いデータ、折り返し、ホバーと書いてあれば、デザインファイルに無くても設計に含める。

件数の違いや 0 件のように、依頼文にもデザインにも無いデータの状態は、未確定として残してデザイン担当に確認する。このスキルが決めている見た目までは未確定に戻さない。

振る舞いがファイルで決まっていないときは、依頼で渡された実在のサイトを参考にしてよい。借りるのは振る舞いだけで、見た目はデザインファイルに従う。

同じデータの表記が1画面だけ違うときは、デザインファイルを直さず、実装でサイト全体の形に揃える。投稿日の実例は `YYYY.MM.DD`（例 `2024.04.24`）である。本文中の日付（令和の表記や「12月1日（月）」など）は投稿日ではないので、この形にしない。

同じ意味の操作文言が画面ごとにゆれているときは、デザインファイルの文言を残さず、サイト全体で1つの言い方にする。記事本文のように内容そのものの文言は、デザインファイルの文言を使う。担当者がすでに直した文言は正とし、あとから渡された仕様の表の文言へ戻さない。

デザインファイルのホバーは、そのまま採るとは限らない。採ったもの、採らなかったもの、却下した案はコミットに残す。依頼者が戻すと言ったら戻す。

## 見比べる

デザインの画像がある画面は、実装した画面をその画像と見比べてから先へ進む。画像が無い画面（管理画面など）は、動いているページを人が見られる状態にして見せ、無い画像を待って止めない。ページを出せないときは、出せない原因を直す。見比べは、人が目で見ることと、貼られた画面への指摘で行う。差分画像は要らない。

幅は、特定の値だけで見ない。端末の幅は揃わない。狭い端から広い端まで動かし、折り返しや段組みが変わる前後も見る。和文は、その途中でも文節の途中で割れていないこと。ページ全体を2倍で書き出して見比べない。

完了条件は、画像がある画面では見比べたこと、そしてテストと CI の通過である。スクリーンショットの有無だけを完了条件にしない。

## 検査、コメント、コミット

機械で検査できるルールは lint や検査に移し、違反メッセージに理由と直し方を書く。文章と検査を二重に持たない。移したら、このスキルの該当文を削る。IDE の警告も、拾えるなら検査に入れる。色の一回きりの値を落とす検査は、サイズとグリッドまでは見ない。名前がある寸法を、別の検査で落とすのはよい。

渡し忘れは隠さない。型があるときは型で落とし、既定値や既定の画像で埋めない。

コメントは、あえてやらなかった理由だけにする。意味は名前で表す。

定数を書き写しただけのテストと、文言や幅を名指しで固定するテストは書かない。禁止する表記のゆれは、サイトの用語集を1つ作り、検査で落とす。用語集に無いゆれは、見比べで見る。

担当者が直接入れたコミットは、戻す指示が無い限り戻さない。

コミットメッセージは日本語で、意図、決めたこと、却下した案が分かるように書く。`intent`、`decision`、`rejected` と書いてよい。

ドキュメントはコードと突き合わせて直し、違う記述と古い記述は削る。

このスキルに書いた判断は、ライブラリの定石で上書きしない。書いていない判断は、公式のベストプラクティスや有名な UI ライブラリ、デザインシステムと照らして決める。聞かれたら変更の目的を説明する。
